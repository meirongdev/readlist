# 实现评审 —— 2026-08-05

> 评审对象: MVP 全部实现（约 3,500 行 Go + 内嵌 SPA + kind 清单），基线 commit `207009b`
> 评审口径: 只问一个问题 —— **这份实现兑现了 [system-design.md](system-design.md) 的承诺吗？**
> 结论: 三层管道、逐维证据、原子发布、确定性理由串确实落地了，`make check` 全绿；
> 但有 **4 个阻塞级缺陷**（其中 3 个是「文档明确要求、代码没做到」），以及 8 项上真实语料前必须处理的问题。
> 本文记录发现与**已完成的修法**；上一轮的文档评审见 [review-2026-08-04.md](review-2026-08-04.md)。

先说好的部分，因为它决定了下面的语气：`system-design.md` 的三层切分不是纸上分层 ——
`facts → judgement(dim_scores + norm_cdf) → selection(lists)` 在代码里是三个真实的边界，
`score` 命令确实不发网络请求，`published_run` 单行指针确实在单事务里最后切，
理由串确实是零 LLM 的确定性拼装。测试也打在了正确的接缝上。下面的问题都是在这个水准之上的问题。

## 一、阻塞级

### A1 同一份语料，两次 `score` 出的榜单成员与顺序都不一样

**实测**：连续两次 `score`（数据零变化），`library-hygiene` 两个 run 的 23 本书成员不同、
顺序不同 —— 并列 TBS（6.0 / 22.0 / 68.0）的书整体洗牌，多样性约束再把随机顺序放大成成员差异。
`reason` 串里「缺：X、Y」的顺序也每次不同。

**根因**三处，都是同一类错误 —— 依赖了 Go map 的随机迭代序：

| 位置 | 问题 |
|------|------|
| `engine.selectList` | `for id, w := range inputs` 构建候选，顺序随机 |
| `selection.Select` | `sort.SliceStable` 没有并列打破键 → 同分书的次序 = 传入顺序 |
| `score.Combine` | 遍历 `weights` map → `Missing`/`Available` 顺序随机 |
| `computeParams` | 遍历 map 做**浮点累加** → 先验值最低位不同，可能翻转并列比较 |
| 四个 loader | `SELECT` 无 `ORDER BY` → 评分/提及的浮点求和次序不定；「取最优出版社/格式」在并列时先到先得 |

这直接废掉 NFR-10「逐位可复现」—— 而 run / diff / corpus_id 这一整套治理机制的存在理由就是它。
真实语料下并列平台更大（~1,500 本无外部评分的书会全部落在同一个先验值上），
公开榜每夜都会无因洗牌，`readlist diff` 每天报假差异。

**修**：`AllDims` 与排序后的 `work_id` 成为所有跨维度/跨 work 循环的唯一遍历顺序；
`selection.Select` 加 `work_id` 升序作终极 tie-break；五条 `SELECT` 全部补 `ORDER BY`。
`TestComputeIsBitwiseReproducible` 连算 6 次比对榜单 + 逐维得分 + 指纹；
`TestSelectionTieBreakIsStableAcrossInputOrder` 打乱输入顺序验证结果不变。

### A2 `grade == "D"` 又成了全局准入闸门 —— review B1 的原病复发

`engine.selectList` 对**所有** preset 一律 `grade == "D" → continue`，`catalog` 同样剔除。
而 grade D 的定义是「F **或** T 为 unknown」。于是 `pubdate` 来自 mtime 兜底的书被排除在
**不使用 F 维**的 `timeless` 之外 —— 这正是 [review-2026-08-04](review-2026-08-04.md) B1
判定为「模型错了」、system-design §2 明文修掉的问题（「字母降级为 UI 徽章，**不再决定任何准入**」）。

演示语料里的活例：`RESTful Web APIs`（O'Reilly、A/C/T 全 measured、有 HN 提及）
仅因 `mtime-fallback` 就整站消失。demo 里是 3 本，真实语料是 **477 本（23%）**。

**修**：准入只剩 preset 的 `filters` + `needs` + `min_coverage`（这套本来就已实现且正确）；
字母只做徽章。目录页收全库并逐本标注缺哪几维。同步改掉 `requirements.md` FR-25 与
`scoring-standard.md` §5 里与 system-design §2 冲突的表述 —— **这三份文档此前互相打架，
代码挑了组合起来最糟的那个语义**。

**验证**：`TestUntrustedPubdateStillEntersTimeless` 断言那本 F-unknown 的 O'Reilly 书
以 coverage 1.00 进入 `timeless`（因为该榜压根不加权 F）；e2e 里也有对应断言。

### A3 「不公开」在 `/api/v1/works/{id}` 上被绕过；matrix 把不存在的 run 也长缓存

`works` 端点没有任何 grade 检查，而 `work_id` 是可猜的 `姓氏/标题` slug ——
`GET /api/v1/works/richardson%2Frestful%20web%20apis` 返回 200 与全量得分。
这是 review M5 警告的「承诺被前端实现方式绕过」，只是换了个端点。

同类：`matrix` 对**任意** run_id（含不存在的）返回 `200 + Cache-Control: immutable`
（实测 `matrix/no-such-run` → 200 空数组 + 永久缓存），也不校验 run 是否存在。

**修**：A2 把可见集合统一成「全库 + 逐维标注」之后，works / catalog / matrix 三个端点
同源，泄漏面消失（不再有「秘密的书」这个概念）；`matrix` 改为校验 run 存在，
否则 404 且不带缓存头。四个内容 handler 收敛到一个 `snapshot()` 入口，错误只处理一次。

### A4 SPA 的核心卖点「权重滑块」整个是坏的

**数据契约断裂**：`/api/v1/lists` 只返回 `{id, name, description, size}`，而 `app.js`
读 `currentList.weights` → 恒为 `{}`。后果链：滑块一个都渲染不出来 → `rescore()` 在
`totalW = 0` 下把**每本书的 TBS 与 coverage 都覆盖成 0** → 首页所有书显示
「0.0 分 · 覆盖 0%」。叠加的问题：重排后位次不更新；`reason` 是唯一没过 `esc()` 的插值；
「重置」按钮调用了不存在的 `renderPage()`；`route()` 的 `return` 没 `await`，
异步失败会逃出 catch 让页面停在「加载中」；`unknown` 维度在详情页被印成 `0.0`。

**为什么漏网**：e2e 对前端只做了 `curl / | grep readlist` —— 「kind 端到端验证通过」
对 SPA 而言只验证了 `index.html` 能返回。

**修**：`/api/v1/lists` 与 `/lists/{id}` 随榜返回 `weights` / `bands` / `order` /
`min_coverage` / `needs`（`preset.Band` 补 json tag）；滑块重排后重新编号，
`coverage` 低于门槛的书退出并显示隐去数量；`unknown` 一律显示「—」。
新增 `scripts/spa-parity.js` + `make test-spa`：在 node 里加载**真正的** `app.js`，
用真实后端响应驱动它，逐本比对客户端与后端的 TBS/coverage/位次 ——
目前覆盖 7 份榜、51 本书，全部逐位一致。这条校验进了 `make check` 与 e2e。

## 二、重要

| # | 问题 | 修法 |
|---|------|------|
| B1 | **run 永不回收**：每夜 ~1.5 万行（2,054 × 7 维 + CDF + 榜单），一年 ~550 万行，100Mi PVC 撑不到三个月 | `gcRuns` 在发布同一事务里保留最近 `KEEP_RUNS`（默认 5）个 run；新增 NFR-17 |
| B2 | **A 维多源合并偏离规格**：逐源各收缩一次再加权平均，把同一本书的评分人数拆散 → 多版次/多源的书被系统性低估（review M6 的失真） | 先在 work 级汇总 `Σv` 与人数加权均分，再整体收缩**一次** |
| B3 | **`MidRankPct` 不是 mid-rank**：`equal/2` 是整数除法 → 奇数并列组少半个名次，无并列时退化成 min-rank（n=1 时唯一的 measured 值拿 0 分位） | 改浮点；顺带用二分把 O(n²) 降到 O(n log n) |

## 三、工程卫生（已随手清掉）

- **死代码**：`api.splitShell`、`config.SourceMetadataDB/SourceAppDB`（无消费者）、
  `publisher.go` 里永不可达的 `"oreillymedia"` 与拼错的 `"sypress"`（本该是 `sybex`）；
  `corpus.TopicKeywordHalfLife` 定义了却从未接线 → 收进 `HalfLifeFor` 规则链。
- **API 层大量吞错**：`lists`/`catalog`/`matrix` 把 error 丢进 `_`，`loadDims` 出错返回空 map ——
  DB 故障时表现为静默 200 + 空数据。现在统一 `slog.Error` + 500。
- **两套 work 聚合逻辑已漂移**：引擎取「最优 tier 出版社 / 最优格式」，API 取「第一行的值」，
  于是详情页展示的出版社可能不是打分用的那个。`corpus.Publisher` / `corpus.FormatRank` /
  `corpus.FormatReadability` 成为唯一实现，两边共用；三个出版日期（`FirstPubdate` /
  `LatestPubdate` / `TrustedPubdate`）各自的用途写进类型注释 —— 顺带修正
  `min_age_years` 该看**最早**版次（1996 年的经典出了 2024 年新版，它依然够老）。
- **坏外链**：`works` 端点把书名直接拼进 URL 路径，带空格即坏链，且 Google Books 的
  路径格式本身不对。改为有强标识符走 volume id / ISBN，否则走**转义后的**搜索串。
- **`standard_version` 在四处硬编码 `"1.0"`**，而 `cfg.StandardVer` 就在旁边 → 改为从
  已发布 run 的 `runs.standard_version` 读取（那才是真相）。
- **`Makefile` 的 `docker-build` 本地不可用**：用 buildx 跑双平台却既不 `--load` 也不
  `--push`，镜像哪儿都没有，紧接着的 `kind load` 必然失败（e2e 脚本自己用普通
  `docker build` 绕开了）。拆成 `docker-build`（本机单架构、落本地 daemon）与
  `docker-buildx`（多架构 + `--push`）。
- **`serve` 的启动失败被吞掉**：端口占用只打一行日志然后挂着等信号 → readinessProbe 一直红
  但容器看起来在跑。改为让进程失败退出。

### e2e 脚本自身的三个缺陷

改完断言之后跑 `make e2e`，发现验证脚本本身比被测代码更不可靠 —— 这三条都会让 e2e
**假通过**，所以单列出来：

1. **复用集群时一直在验证上一次的二进制。** 镜像 tag 不变（`readlist:dev`）→ Deployment
   spec 无变化 → `kubectl apply` 报 `unchanged`，旧 pod 继续跑。加 `rollout restart`；
   并默认重置 PVC，因为旧数据卷上留着上一版代码打出的 run，而 `readlist init` 现在是幂等的。
   （删 PVC 时必须先删 Job —— 已完成的 CronJob pod 仍算 PVC 使用者，会让 PVC 永久卡在
   `Terminating`，`--wait` 就此挂死。）
2. **`set -o pipefail` + `grep -q` 把成功的断言判成失败。** `grep -q` 命中即退出，上游
   `curl` 收到 EPIPE 非零退出，pipefail 让整条管道失败 —— 响应体越大越容易踩到
   （matrix 有几十 KB，正是它先暴露的）。改成「先抓进变量，再判断」，脚本里 6 处同类隐患一并消除。
3. **`HOME=$(curl …)` 覆盖了 `HOME` 环境变量**，于是后面的 `kubectl` 找不到
   `$HOME/.kube/config`，报出「context "kind-readlist" does not exist」—— 一个与真实原因
   毫无关系的错误信息，排查花了三轮。

顺带让 e2e 通过 `kubectl create job --from=cronjob/readlist-score` 触发重算：既验证了
**夜间 CronJob 的 env 与卷挂载**（此前全程没被测过），也保证断言一定打在当前二进制的产物上，
并顺势断言「重算后 `published_run` 指向新 run」，也就是原子发布确实生效。
SPA 一致性校验走 `port-forward`，因为 node 的 HTTP 客户端在本机 Docker 网桥网段上会挑一个
无效源地址（`Local (x.x.x.0:…)` → `EHOSTUNREACH`），而同一地址 curl 是通的。
