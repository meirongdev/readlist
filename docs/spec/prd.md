## 1. 背景与问题

私有 Calibre-Web 书库（`book.meirong.dev`）积累了 **2,054 本**技术书。真正的问题不是
"书不够"，而是**没有排序能力**：

| 痛点 | 现状 |
|------|------|
| 书库不会推荐 | calibre-web 只能按标题/作者/添加时间排，回答不了"下一本读什么" |
| 本地评分等于不存在 | 库内评分只有 **14 本** |
| 外部榜单是别人的书 | Goodreads / Amazon / HN Books 排的不是我的库，且全是 1–2 维死榜 |
| 技术书两个特性被通用榜无视 | **会过时**（React 18 的书和编译原理的书，"三年前出版"含义不同）；**分层级**（深度不是越高越好，取决于目标） |
| 阅读状态近乎空白 | 只有 **23 本**标了已读（1.1%），且状态分散在另一个库里 |

结果：书库变成"下载即遗忘"的堆积。

## 2. 产品定位

**一句话定位**：一个"会过时、分层级"的技术书**多维评分**标准 + **可自调口径**的公开书单站；
只发**元数据与评分，不发书**。

三个价值主张：

1. **多维而不是一维** —— 时效按主题半衰期衰减、深度按目标带打分，这两点正好是通用书榜最薄的地方；
2. **榜单是权重档案，不是写死的排序** —— 同一份分数，读者自己调权重就能得到不同答案；
3. **可解释、可复算、可信** —— 证据分级 + 每个分数可追溯到原始来源，自建榜唯一的信任来源就是"能看见怎么算出来的"。

## 3. 目标与非目标

### 目标

1. 一套**可解释、可复算、版本化**的技术书评分标准（维度 + 组合规则，而非一个死分数）；
2. 同一批分数下切换**不同评分口径**看不同榜单，读者可自行调整权重；
3. 一个**公开**书单 Web 应用：免登录浏览榜单、查看每本书的得分拆解与数据来源；
4. 每本书标出**是否已阅读**，可筛选，并派生「下一本读什么」阅读队列。

### 非目标

| 不做 | 原因 |
|------|------|
| ❌ 公开下载 / 在线阅读 / 正文片段 | 版权红线（NFR-12） |
| ❌ 替代 calibre-web | 本站只读它的元数据 |
| ❌ 用户注册 / 投票 / 评论 | 无流量则无数据可排；写接口只增攻击面 |
| ❌ 在本站修改阅读状态 | 真相源必须唯一 |
| ❌ 全量书评生成 | LLM 只做结构化标注，不面向读者写评价 |

## 4. 目标用户与核心场景

| 角色 | 关心什么 | 核心场景 |
|------|---------|---------|
| **库主人**（唯一写入者） | 下一本读什么；哪些书元数据烂；读过的书留下痕迹 | 打开「下一本读什么」→ 高分 ∩ 未读；补元数据；标已读 |
| **公开访客**（无登录） | 某个方向有哪些书值得读；这个排名凭什么；哪些是作者真读过的 | 切书单 → 看口径（这个排名按什么算）→ 点开书看得分拆解 |
| **运维**（同一人） | 采集不炸、配额不爆、公开端点不被爬垮 | 看指标；处理配额耗尽；确认榜单没静默过期 |

## 5. 成功指标

### 北极星

> **「下一本读什么」的周使用次数**（对库主人）与**书详情得分拆解展开率**（对访客）。

前者是项目对库主人最大的价值落点；后者是公开站"可解释"承诺是否被真实使用的证据。

### 行为指标

| 指标 | 目标 |
|------|------|
| 公开榜周 UV / PV | 上线后建立基线，不预设目标 |
| `to-read-next` 周使用次数 | 持续 > 0（库主人自己在用） |
| 书详情得分拆解展开率 | 详情页 PV 的 ≥ 60% |
| 「关于」页 PV / 榜单页 PV | 访客是否在看「分数怎么读」—— 可解释性是否真的被消费 |

### 护栏指标（防退化，不达标即告警）

| 护栏 | 定义 |
|------|------|
| 零版权事件 | 公开站 0 次下载 / 在线阅读 / 正文片段请求 |
| 零写接口 | 0 次对非 GET API 的成功调用 |
| 配额不超额 | 外部 API 0 次超额 / 空转 429 |
| 榜单不静默过期 | 最后一次成功采集时间戳永续更新 |
| 数据质量 | `mtime-fallback` 书数 → 0；孤儿行数平稳；A/B 级书数达预期（约 700–900） |

## 7. 用户故事

1. 作为库主人，我想看到「高分但我还没读」的书，以便决定下一本读什么。
2. 作为库主人，我想标记 已读/在读/想读/弃读/精读，并让榜单反映出来。
3. 作为库主人，我想知道哪些书元数据残缺，以便去补。
4. 作为库主人，我想给已读的书补个人星级，让「我读过且推荐」榜有内容（该榜还需 LLM 标注落地，见 FR-31b）。
5. 作为访客，我想按不同口径切换书单（当前：经典长青 / 近一年新书 / 下一本读什么）。
6. 作为访客，我想知道这个排名到底按什么算的 —— 权重应当写在页面上，而不是藏在后台。
7. 作为访客，我点开某本书要能看到它凭什么排这么高 —— 各维度分 + 数据来源。
8. 作为访客，我想知道哪些书作者真读过 —— 真人读过的推荐比算法分可信。
9. 作为访客，我不想看到"数据不足硬凑出来"的书混在榜里。
10. 作为运维，我要在配额耗尽 / 采集失败时知道，而不是发现榜单静默过期。
11. 作为访客，我不想在公开站看到正文、下载或跳转私有书库的入口。
12. 作为库主人，我不想本站二次写入阅读状态，导致状态分叉。

## 8. 关键产品决策

| # | 决策 | 理由 |
|---|------|------|
| D-1 | **只发元数据与评分，不发书**；封面外链不自托管 | 版权红线；"去哪读"只给出版社 / Google Books 外链 |
| D-1b | **公开面 = 公开榜单的并集，不是全库**：只展示推荐书单与上榜书的元数据 | 产品是"书单"不是"书库"；把两千本私人藏书逐本枚举出去既不是意图，也让公开面远大于内容本身 |
| D-2 | 评分 = 维度事实 + 权重档案；**榜单 = 权重向量**，加榜不改代码不重算分 | 一个分数支撑多个口径 |
| D-3 | **证据分级 A/B/C/D 只做徽章，不决定准入也不决定公开范围**：字母之外，逐维状态才是硬门（见 D-1b：公开范围由"是否上榜"决定） | 宁可百来本可信书单，不要掺猜测分；但把逐维证据压成一个字母去卡全局，会误杀 23% 的书（review B1） |
| D-4 | 阅读状态**只读镜像**，真相源恒为 calibre-web；facet 不进 TBS | 已读 ≠ 好书；单写入点防分叉 |
| D-5 | **标准版本化**：改公式/权重 = 发新版，历史分保留，逐位可复算 | 榜单可信度的根基 |
| D-6 | **口径公开，但不可调** —— 权重印在书单页上，访客不能改 | 可解释性的价值在「看得见」，不在「能拖动」。让访客改权重要么只能在已选出的 20 本内换序（做不到他真正想要的），要么得对全库重跑选材（正是 D-1b 不提供的入口）；而代价是把 `score.Combine` 实现两遍。原滑块已撤除 |
| D-7 | 单 Go 二进制复用 `trends` 部署形状（cron 采集 + 评分 + 内嵌 SPA + SQLite/ARM/Recreate） | 已验证的部署路径，不发明新形状 |
| D-8 | 域名 **`readlist.meirong.dev`**，不用 `books.` | 与私有书库 `book.meirong.dev` 只差一个字母，误配代价高 |

## 9. 发布计划

| 期 | 交付物 | 谁 | 验收入口 |
|----|--------|-----|---------|
| **Phase 0** | 阅读状态补录：建 3 个书架、补 54 本候选、23 本已读补星级 | 库主人（手工） | AC-P0 |
| **Phase 1** | 元数据修复：pubdate 来源重跑、出版社归一表 | 库主人（homelab 脚本） | AC-P1 |
| **Phase 2** | 离线打分管线：A/F/T/L → 阅读队列 → C 维 → D/P 维 | 开发 | AC-P2 |
| **Phase 3** | Web 应用 + 公开：榜单/详情/目录/API、限流、清单登记 | 开发 | AC-P3 |
| **Phase 4** | 收尾：指标进监控、标准定版、PVC 入夜备 | 开发 | AC-P4 |

依赖：**Phase 1 是唯一硬阻塞**（不做则时效维度不可用）；Phase 0 纯手工、与代码并行。

## 10. 风险与依赖

最高风险（完整登记见 [roadmap.md](../roadmap.md)）：

| 风险 | 影响 | 缓解 |
|------|------|------|
| ⚠️ `pubdate` 污染未修就上时效维度 | "今年新书"榜塞满老书，整站可信度一次性崩塌 | Phase 1 设为阻塞；不可信记"未知"、压 C 级 |
| ☠️ 整库快照 `app.db` | 密码 hash / OIDC 凭据泄露到公开服务 | 最小导出 3 张表；写进代码 review 清单 |
| HN 标题误匹配 | 榜单显得随机 | 精确短语 + 共现约束 + 人工白名单 + 可否决 |
| 外部配额耗尽 | 首轮采集卡住 | 持久化缓存、退避、当日用尽即停 |
| LLM 标注质量不足 | 深度/可操作维失真 | 强制 schema + 置信度门槛 + 最坏退 4 维 |
| 公开端点被爬垮 | 带宽/CPU 被吃 | 边缘限流分档、应用只读、封面外链 |
| 阅读状态长期只覆盖 1% | 徽章与阅读队列形同虚设 | Phase 0 独立推进；接 KOReader 让"在读"自动产生 |

## 12. 术语表

| 术语 | 含义 |
|------|------|
| TBS | Tech Book Score，本文档所在项目的技术书评分标准（当前 v1.0） |
| 维度 A/C/F/T/D/P/L | 口碑 / 技术圈声量 / 时效 / 权威 / 深度 / 可操作 / 馆藏可读性 |
| preset | 榜单预设 = 权重 + 目标带 + 过滤器 + 豁免维度的权重档案（YAML） |
| 证据等级 A/B/C/D | 决定一本书能否上公开榜及如何标注 |
| facet | 参与筛选展示、但不进 TBS 分数的属性（如阅读状态） |
| 目标带 | 对"深度"这类有最优值的维度打分：偏离目标值扣分，而非单调加权 |
| 贝叶斯收缩 | 缺数据时收缩到语料先验，而不是当 0 分处理 |
| `VACUUM INTO` | SQLite 一致性快照命令（metadata.db 是 WAL，只能这样读） |
| 最小导出 | 从含凭据的 `app.db` 只导阅读状态相关 3 张表，绝不整库快照 |
