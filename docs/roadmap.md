## 1. 分期计划

分五期，**每期自身可交付**，不做一次性大爆炸。

### Phase 0 — 阅读状态补录（只有库主人能做，越早开始越好，**不阻塞其余各期**）

纯手工，与写代码并行。做不做决定「已读徽章」和「下一本读什么」榜有没有内容。

1. 在 calibre-web 建 3 个书架：`想读` / `弃读` / `精读`
   （[reading-status.md §3](reading-status.md#3-状态模型核心三态--书架承载扩展状态)）。
2. 跑 [reading-status.md §6](reading-status.md#6-补录历史阅读记录真正的工作量) 的候选清单 SQL
   （54 本），在 UI 里逐本标已读 / 想读 / 弃读。
3. **给已读的 23 本补个人星级** —— 这是 `read-and-loved` 榜的唯一输入（现在只有 3 本）。
4. 可选但值得：查一遍笔记系统里的书籍笔记能对上多少本。
5. 长期：接 KOReader + kosync（`kosync_progress` 现 0 行），否则 `◐ 在读` 永远是空的。

### Phase 1 — 元数据修复（**阻塞**：不做则时效维度不可用）

1. 重跑元数据富集，这次**记录 `pubdate_source`**（写入日期时同时写来源）。
2. 优先用 Google Books（310 个 volume id + 715 个 ISBN），OpenLibrary 兜底。
3. 建 `publisher_map`：Packt 4 变体、O'Reilly 2 变体、BPB 2 变体归一（一次性人工 + 后续规则）。
4. 产出核对：`pubdate_source='mtime-fallback'` 还剩多少本
   —— **这个数直接决定 A/B 级书的上限**。

> 富集脚本本身在 homelab 仓库（`calibre-metadata` 那套清单）里，不在本仓库。

### Phase 2 — 离线打分管线（无 UI，先证明分数靠谱）

1. 快照 CronJob（`VACUUM INTO` + `app.db` 最小导出）+ [architecture.md §4](architecture.md#4-数据模型sqlite) 的表结构。
2. 实现 **A / F / T / L** 四维（**纯数据，不依赖 LLM**）→ 先出一版 `timeless` 榜。
3. **接阅读状态 → 立刻能出 `to-read-next` 榜。**
   这一步几乎零成本，却是整个项目对自己最有用的产出，**别排到最后**。
4. **人工验收**：拿 20 本自己熟的书对一遍排名。榜首若出现明显不该在的书 → 回头改公式，
   **不要靠调权重糊过去**。
5. 再加 **C** 维（HN 提及）—— 单独一步，因为误匹配需要独立验收：
   抽 30 本人工看命中的讨论对不对。
6. 最后加 **D / P**（LLM 标注）。

### Phase 3 — Web 应用 + 公开

1. 内嵌 SPA：榜单页（预设切换 + 权重滑块 + **阅读状态徽章/筛选**）、
   书详情页（**得分拆解 + 数据来源 + 标准版本**）、全库目录页（含 C 级书，标"数据不足"）。
2. 清单进 homelab 仓库并在 kustomize 树里**登记**；HTTPRoute + 导航页条目 + 可用性监控。
3. Cloudflare 限流（页面 / `/api/` 分档）。
4. `readlist-data` 加进夜备名单（CI 规则 H4 会拦）。

### Phase 4 — 收尾

1. 指标接入监控（采集成功率 / 配额消耗 / 各证据等级书数 / 孤儿行数）。
2. 评分标准定版为 `1.0`，此后改动走 [scoring-standard.md §8](scoring-standard.md#8-版本治理) 的版本治理。
3. homelab 侧的服务清单与开放项列表更新。

## 2. 依赖关系

```
Phase 0（补录）   ──┐  纯手工，随时开始，与代码并行
                    ├──► Phase 2 的第 3 步（to-read-next 榜）
Phase 1（修 pubdate）──► Phase 2 的 F 维度 ──► fresh-releases 榜
Phase 2 ──► Phase 3 ──► Phase 4
```

**Phase 1 是唯一的硬阻塞**，且它的工作发生在 homelab 仓库而不是这里 —— 排期时别忘了。

## 风险登记

### R-1 ⚠️ `pubdate` 污染未修就上时效维度

| | |
|---|---|
| **影响** | "今年新书"榜塞满 2018 年的老书；整站可信度一次性崩塌 |
| **概率** | 高（477 本已受影响，且错误值不会报警） |
| **缓解** | Phase 1 设为阻塞前置；来源不可信的书时效记"未知"、证据压 C、不参与按时效排序的榜 |

这是本项目**最容易被忽略、后果最严重**的一条。缺失数据会暴露自己，错误数据不会。

### R-2 ☠️ 整库快照 `app.db`

| | |
|---|---|
| **影响** | 密码 hash（2 行）、会话（2 行）、OIDC 凭据（3 行）落到公开服务能读到的卷上 |
| **概率** | 中 —— 这是"图省事就会犯"的错，`VACUUM INTO` 整库比写三条 SQL 省事 |
| **缓解** | [reading-status.md §4](reading-status.md#4--只导出需要的表--appdb-含密码-hash-和-oidc-凭据) 的最小导出；**写进代码 review 清单** |

### R-3 HN 标题误匹配

| | |
|---|---|
| **影响** | 通用短标题（`Clean Code`、`Refactoring`）命中大量无关讨论 → 榜单显得随机 |
| **概率** | 高（本库有相当多 2 词标题） |
| **缓解** | 精确短语 + 作者/出版社共现约束；≤2 词标题走人工白名单；保留 `objectID` 可点开验证与否决；**宁少不多** |

### R-4 外部配额耗尽 / 被限流

| | |
|---|---|
| **影响** | 首轮采集卡住；反复打 429 |
| **概率** | 中 |
| **缓解** | 持久化缓存（重启不重抓）、指数退避、当日配额用尽即停到次日、评分 TTL 30 天 |

### R-5 LLM 标注质量不足

| | |
|---|---|
| **影响** | 深度/可操作维度失真，`ship-this-week` / `deep-dive` 两榜不可信 |
| **概率** | 中 —— 52% 的书没有简介 |
| **缓解** | 强制 JSON schema + 模型自报置信度；`confidence < 0.5` 不用于榜单；抽样人工核对；最坏情况**退回 4 维**（假设 A-3 不成立） |

### R-6 公开端点被爬垮

| | |
|---|---|
| **影响** | 带宽/CPU 被爬虫吃掉 |
| **概率** | 低—中 |
| **缓解** | 边缘限流分档；应用只读无写接口；封面外链不自托管 |

### R-7 版权

| | |
|---|---|
| **影响** | 法律风险 |
| **概率** | 低（只要守住红线） |
| **缓解** | **只发元数据与评分，不发书**：无下载、无在线阅读、无正文片段；封面**外链**而非自托管；与私有书库无跳转关系；"去哪读"只给出版社/Google Books 外链 |

### R-8 book id 漂移

| | |
|---|---|
| **影响** | 阅读状态错配到别的书（删书重导入会让 id 变） |
| **概率** | 已发生 —— 实测 26 行里 **2 行是孤儿** |
| **缓解** | join 时丢弃孤儿；孤儿数写进 `runs` 并纳入监控；长期可考虑用 ISBN/uuid 作稳定键 |

### R-9 阅读状态长期只覆盖 1%

| | |
|---|---|
| **影响** | 徽章、`to-read-next`、`read-and-loved` 全部形同虚设（假设 A-4 不成立） |
| **概率** | 中 —— 取决于补录是否真做 |
| **缓解** | Phase 0 独立于代码、可随时推进；接 KOReader 让"在读"自动产生 |

## 开放问题

| # | 问题 | 倾向 | 什么时候必须定 |
|---|------|------|--------------|
| 1 | 公开范围：只发 A/B 级（约 700–900 本），还是也放 C 级目录页？ | 放目录页，默认榜单不含 C | Phase 3 前 |
| 2 | 中文书（20 本）单独小榜还是并入主榜？外部源对中文技术书覆盖差异大 | 单独小榜 | Phase 3 前 |
| 3 | 个人笔记数要不要作为信号？"做过笔记"比"标了已读"强得多 | 先量能对上多少本再定 | Phase 2 前（若要用） |
| 4 | 镜像更新：可变 tag + 手工重启，还是配 image-updater 写回 digest？ | 后者更规范，但属独立议题 | Phase 3 |
| 5 | `standard_version` 升版评审机制 | 升版必须附「20 本已知书的排名对比」 | Phase 4 |
| 6 | 是否需要"某本书为什么没上榜"的解释页？ | 有价值（证据不足是最常见原因），但非首版 | 首版之后 |
