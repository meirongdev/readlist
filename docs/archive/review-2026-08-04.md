# 文档评审 — 2026-08-04

> 评审对象: 本仓库全部文档（README + docs/ 8 篇 + bdd/ 8 个 feature），**无代码**（git 零 commit）
> 评审口径: 只问一个问题 —— **按现在这份规格实现，能不能产出一份可信的书单？**
> 结论: 地基（data-baseline）扎实，标准（scoring-standard）有 4 处会让首版榜单**算错或算空**的规格缺陷，
> 产品层缺一个「从总序到书单」的选材层。修法见 [system-design.md](../spec/system-design.md)。

先说好的部分，因为它决定了评审的语气：`data-baseline.md` 是实测而非估计，`pubdate` 污染
和 `app.db` 含凭据这两条是自己摸出来的，不是抄的清单；快照 CronJob 隔离 blast radius 的论证
（[architecture.md](../spec/architecture.md) §2）是全套文档里最好的一段。下面的问题都是在这个水准之上的问题。

## 一、阻塞级 —— 不修则首版榜单是错的或空的

### B1 证据等级是单一标量，但证据本身是逐维度的 → 旗舰榜自相矛盾

| | |
|---|---|
| 位置 | [scoring-standard.md:208-213](../spec/scoring-standard.md)（A/B/C/D 表）、`:102`、`:230-231`；[data-baseline.md:125](../spec/data-baseline.md)；[requirements.md:108](../spec/requirements.md)（FR-25） |

三处规格互相打架：

- `:213` 说 `pubdate` 来自 mtime 兜底 → **D 级，不公开**；
- `:102` 与 [data-baseline.md:125](../spec/data-baseline.md) 说 → **压到 C 级**（C 只进目录页）；
- `:230` 说 `timeless` **豁免时效**（`exempt: [F]`），`:231` 又要求 `min_evidence: A`。

于是：一本有 3,000 人评分的 O'Reilly 经典，仅因为出版日期来自 mtime 兜底，就被排除在
**明确声明不关心出版日期**的「经典长青」榜之外。受影响 **477 本（全库 23%）**。

根因不是笔误，是**模型错了**：证据是逐维度产生的（A 维有没有外部评分、F 维 pubdate 可不可信、
D 维 LLM 置信够不够），却被压成一个标量闸门去卡所有榜单。

**修**：证据状态落在 `dim_scores` 每一行上（`measured` / `shrunk` / `unknown`）；preset 声明
「我用哪几维、每维要什么最低状态」；准入 = 该 preset 用到的维度都达标。单一 A/B/C/D 降级为
UI 徽章，不再当闸门。

### B2 `min_evidence: A` 是三个条件的交集 —— A 级可能只有几十本

`:210` 定义 A = 有外部评分且 `v ≥ m` **且** `pubdate_source` 可信 **且** LLM `confidence ≥ 0.7`。

三个筛子相乘，按实测基数估：外部可查上限 ≈ 1,025 本（715 ISBN + 310 volume id，含重叠）→
其中真有评分的更少 → `v ≥ 20` 的更少（Google Books 技术书评分人数普遍是个位数）→ 再交
「pubdate 可信」（排除部分 477 本）→ 再交「有简介才可能高置信」（**52% 的书没有简介**）。

文档说 A/B 合计 700–900 本，这个数没问题；**但 A 单独一档很可能是两位数**。而 `timeless`
是旗舰榜且卡 `min_evidence: A` + `min_age_years: 3`。AC-P2① 的「前 20 人工核对」在候选池
只有几十本时接近走过场。

**修**：**在写 UI 之前先跑一次纯计数的覆盖率 dry-run**（不打分，只统计每维 measured 比例、
每个 preset 的候选池大小）。这是一天的活，能防止把整个前端建在空集上。preset 的
`min_evidence` 应该由那次 dry-run 的真实数字来定，而不是先写在 YAML 里。

### B3 `exempt` 是空操作 —— 而全套文档把它当核心机制

`:199-202` 说权重和为 1、被 `exempt` 的维度「从分母里剔除并重新归一」；
[bdd/ranking.feature:26-29](../spec/bdd/ranking.feature) 专门有一个场景断言这件事。

但 `:229` 的 `timeless` 权重是 `{A:.35, C:.30, T:.20, L:.15}` —— **已经和为 1，F 根本不在里面**。
剔除一个权重为 0 的维度，再把和为 1 的权重「重新归一」，两个操作都是恒等变换。
那个 BDD 场景在现有 YAML 下**不可能被观测到**。

真正需要 renormalize 的场合是**逐本**的：某本书某一维 `unknown` 时，把这一维的权重摊回其余
维度 —— 而不是让它吃一个编出来的先验值。文档想表达的正是这件事（`:201-202` 的注解「不是给
时效权重 0 —— 那会让老书被隐式惩罚」），但落到 preset 层就变成了无操作。

**修**：删掉 preset 层的 `exempt`（显式权重里不写这一维已经表达了豁免），把 renormalize 移到
**逐本**层，并把 `coverage = Σ 可用维度权重` 暴露到前端。

### B4 `bands` 没有权重 —— 目标带对 TBS 的贡献是 0

`:197` 的 `TBS = Σ_i w_i·score_i + Σ_j w_j·band_score(...)`，`:200` 要求权重和为 1。
但 `:235-236` 的 `ship-this-week`：`weights` 四项已和为 1，`bands: { D: {target:35, tol:25} }`
**没有 w_j**。按公式字面，band 项系数为 0 → 「太深的书不适合速成」这个卖点在公式上不成立，
[bdd/ranking.feature:32-35](../spec/bdd/ranking.feature) 的场景不可能通过。

顺带一处定义冲突：`:186-188` 说 facet 维度（D）用目标带，而 `deep-dive`（`:241`）把 D 当单调
维度给了 0.35 权重。「深挖原理 = target 100 的目标带」是自洽的，但规格得选一种写法。

**修**：band 维度也占 weights 里的一项，band 参数单列：

```yaml
weights: { F: 0.25, P: 0.30, A: 0.15, L: 0.10, D: 0.20 }   # 仍和为 1
bands:   { D: { target: 35, tol: 25 } }                    # D 的 0.20 走 band_score
```

### B5 分位归一 + 贝叶斯收缩 = 巨型并列点，而并列规则没定义

FR-22 分位归一（[requirements.md:105](../spec/requirements.md)）+ FR-27 缺数据收缩到先验（`:109`）
两条单独看都对，合起来有个没被处理的后果：若 ~1,500 本无外部评分，它们的 `A_raw`
**全部等于同一个先验值 C**。

1. 分位的并列处理（min-rank / mid-rank / max-rank）会让这 1,500 本整体上下移动几十分。
   规格没写这条 → **NFR-10 的「逐位可复现」不成立**，两个正确实现会给出不同分数。
2. 这 1,500 本参与 CDF 构建，会把真正有数据的 500 本压缩到分位空间的一个窄带里 ——
   本该被放大的信号反而被摊平了。
3. `A_raw` 本身量纲也窄：技术书的贝叶斯加权分几乎全落在 3.9–4.4，分位化会把 0.05 星的差异
   放大成几十分的排名差。这一维的判别力被高估了。

**修**：CDF 只用 `measured` 的行构建并作为**版本化产物**存下来；`shrunk` 的行映射到先验在该
CDF 上的位置且标记出来，不参与 CDF 构建；并列写死用 **mid-rank**。

## 二、重要 —— 会让榜单「不错但没用」

### M1 最重的权重压在最缺数据的一维上，两个自称的差异点在旗舰榜里都没用上

把 7 个 preset 的权重摊开看：**A（口碑）在每个 preset 里都是最高或次高（0.20–0.40）**，
而 A 的覆盖率是 `~35%，最大短板`（`:33` 自己写的）。反过来，T（出版社，覆盖 66%，
[data-baseline.md:69](../spec/data-baseline.md) 称「本库**最可靠的一维**」）只拿 0.20–0.30，
L（100% 可算）只拿 0.10–0.15。

更要紧的是旗舰榜 `timeless` 的构成：`A + C + T + L`，F 被豁免、D 根本没用。
而 F 和 D 正是 `:41-44` 声明的两个差异点。

> 于是「经典长青」榜 = 外部评分 + HN 提及 + 出版社先验 —— **恰好退化成它要打败的那种
> 1–2 维死榜**，只是多了一个出版社加权。

**修**：(a) 用 B2 的 dry-run 量每一维的**实际判别力**（有多少本不是先验值 / 不是 0），按判别力
而非直觉分配权重；(b) `timeless` 至少要让 D 以目标带参与（经典书的深度分布不是均匀的），
或把 T/readability 提上来；(c) 承认「经典长青」这类榜需要一层人工 curation —— 它是**最难**
自动出对的榜，不适合当第一个交付物。

### M2 Phase 1「唯一硬阻塞」其实不是阻塞 —— readlist 自己就能解

[roadmap.md:25,70](../roadmap.md) 把「重跑元数据富集、记录 `pubdate_source`」定为唯一硬阻塞，
且 `:33` 说富集脚本在 **homelab 仓库**。这条依赖是自找的：

readlist 的 fetch worker 为了 A 维本来就要按 ISBN / volume-id 打 Google Books，而**同一个响应
里就带 `publishedDate`**，来源天然是 `google`。readlist 需要的不是「修好 calibre 的
`metadata.db`」，而是「自己 `books` 表里有一个带来源的 pubdate」。

**修**：`books.pubdate` 取值规则改为「外部来源优先；calibre 的值只在能与外部交叉验证时采信；
否则 `unknown`」。回写 calibre 降级为可选的书库卫生任务。**关键路径上少一个跨仓库依赖，
时效维度可以和 A 维同一步交付。**

### M3 可复现性契约漏了「语料」

NFR-10（[requirements.md:169](../spec/requirements.md)）：同 `standard_version` + 同 evidence 快照
⇒ 逐位复现。但分位归一是**语料相对**的 —— 往库里加 30 本书，全部 2,054 本的分数都会变。
一个宣称「可复算 + 版本治理」的站，这个漏洞会直接被自己的历史分对比打脸。

**修**：`dim_scores` 带 `corpus_id`（快照 books 集合的 hash）与 `run_id`；CDF 存成产物；
前端能区分「分数变了因为公式变了」和「因为语料变了」。

### M4 `scores` 按 preset 存综合分，与 FR-30「加榜不重算分数」冲突

[architecture.md:88-89](../spec/architecture.md)：`scores(book_id, standard_version, preset_id, tbs, ...)`。
既然 `TBS = f(dim_scores, preset)` 是纯函数，存下来就意味着**加一个 preset 要跑一遍写库**，
而 FR-30 明说「加榜不改代码、不重算分数」。

**修**：只持久化 `dim_scores`。榜单不是点积结果而是**选材产物**（含去重与多样性约束，见 §三），
存 `lists(run_id, list_id, rank, work_id, reason)`。

### M5 客户端滑块重排的数据契约没定义，且与「C/D 级不公开」冲突

NFR-2 要求浏览器内重排、零网络往返 → 必须把 **books × dims 整个矩阵**发给客户端。
2,054 行 × 7 维 + facet ≈ 200–400 KB JSON / 60–100 KB gzip，完全可行 —— 但这是个设计决定，
现在没写。

而且：**矩阵里绝不能含 C/D 级行**，否则 devtools 里就能看到「不公开」的书 ——
FR-25 的承诺被前端实现方式绕过了。

**修**：`GET /api/matrix/{run_id}.json`，immutable + 长缓存，**只含可公开行**；滑块只在这份
矩阵上做点积。

### M6 没有版次去重 → 同一本书的多个版次会同时上榜，且评分人数被拆散

Google Books 的评分挂在 volume（版次），OpenLibrary 挂在 work（作品）。不做 edition→work
归并有两个后果：`v`（评分人数）被拆到各版次 → 贝叶斯把书往先验拉回去（本该有 3,000 人评分
的书按 600 人算）；书库里同书两个版次 → 榜上两行。对一份**书单**来说，
「Learning Python 4th / 5th 各占一行」是肉眼可见的质量缺陷。

**修**：引入 work 级实体，聚类键 `OpenLibrary work id > ISBN-13 族 > normalize(title)+首作者`；
评分在 work 级求和；榜单在 work 级出；详情页列出本库持有的版次与格式。

### M7 L 维不该进面向读者的榜

`L = 30·format + 20·has_cover + 20·has_comments + 15·has_isbn + 15·metadata_complete`（`:162`）。

后四项说的是**「我的私有库元数据全不全」**，对公开访客零信息量 ——
「这本书在我的 Calibre 里有没有简介」不是书的属性。而 `has_isbn` 又与 A/B 准入高度相关，
在 `timeless` 里等于把同一个 ISBN 信号计了两遍（一次当闸门、一次当 0.15 权重）。

**修**：公开榜只用 `format_score`（EPUB vs PDF 确实影响读者体验），改名 `readability`；
完整的 L 留给 `library-hygiene` 内部榜 —— 这也正是文档自己给 L 的第二用途（`:167`）。

### M8 F 的方差被一个未经验证的离散 LLM 标签支配

`half_life` 由 `topic_class` 一档定死，25 年 vs 1.5 年（`:90-96`）。同一本 3 年前出版的书，
标错一档 → F 从 92 掉到 25。项目把 F 称作核心差异点，却把它整个压在一次性 LLM 分类上，
而 R-5 的缓解只有「模型自报置信度」—— 自报置信度是已知校准很差的东西。

**修**：`half_life` **规则优先**：BISAC 码前缀（[data-baseline.md:70-80](../spec/data-baseline.md)
已确认标签是结构化 BISAC）+ Top ~40 主题关键词表 → 命中即定档；LLM 只处理未命中项，
且结果进人工复核队列。另外准备 60–100 本**人工 gold 标注**（按有无简介、按主题分层抽），
量 `topic_class` 准确率与 `depth` 的 Spearman 相关；不达标 D/P/F 不上公开榜。

### M9 `min_personal_rating: 4` 语义未定，且它的输入在管道里不存在

`:266` 的 `min_personal_rating: 4`：Calibre 的 `books_ratings_link.rating` 存的是
**0–10（星 × 2）**。所以 `4` 是 4 星，还是 rating=4（= 2 星）？这是个必然踩的坑。

更要紧的：**FR-1x 里没有任何一条说要摄入 `books_ratings_link`**，
[architecture.md:81](../spec/architecture.md) 的 `books` 表也没有 rating 字段。
`read-and-loved` 榜的唯一输入在整条管道里不存在。

**修**：补一条 FR + 一个字段，单位在规格里写死为「星（0–5，metadata 值 ÷ 2）」。

### M10 F 公式没有夹逼上界

`F = 100·0.5^(age/half_life)`（`:85`）。477 本被 mtime 写成 2026 年，今天是 2026-08-04 ——
其中一部分 `pubdate` 落在**未来** → `age < 0` → `F > 100`，破坏 0–100 不变量，
并且这些书会排到榜首。

**修**：`age = max(0, now − pubdate)`；`pubdate` 在未来直接判 `unknown` —— 未来日期本身就是
污染的强信号，可以拿来交叉校验（补 [data-baseline.md:126](../spec/data-baseline.md) 的第 3 条处置）。

### M11 `engagement` 导出了却没人消费；`to-read-next` 的过滤器几乎不起作用

[reading-status.md:116-118](../spec/reading-status.md) 专门导出了 `downloads`（40 本，弱信号「打算读」），
但**没有任何维度或 preset 消费它**。「想读」书架同理 —— 建了、导了、没用。

而 `to-read-next` 的过滤器只有 `read_status: [unread]`，未读 ≈ **99%** →
这个过滤器基本是恒真，`to-read-next` 与 `timeless` 的差别很薄。它却是文档反复强调的
「对库主人最大的价值」和北极星指标。

再看它的权重（`A/C/T/P/L`，`:259`）：**不含 F 和 D** —— 而个人选「下一本读什么」最敏感的恰恰
是「会不会已经过时」和「深度合不合我现在的水平」。

**修**：`to-read-next` = 未读 ∩ 意图信号加权（想读书架 > 下载过 > 无）× F 参与 × D 走
目标带（目标值由用户选的 level 决定）。把 intent 做成显式 facet，而不是导出后丢掉。

## 三、产品层最大的缺口：产品是「书单」，机制是「排序」

这一条不是 bug，是 review 里最值得改的一处，也是 `system-design.md` 的出发点。

全套文档的输出单元是**一个总序**（preset → 按 TBS 排序的 2,054 行）。而「书单」的形状不是总序。
在总序上直接切 top-20，会得到：20 本里 9 本 Kubernetes、同一本书的 3 个版次、
以及若干只是因为「有 ISBN + O'Reilly + 被提及 3 次」而排上来的填充书。

好书单的形状是 **`(目标 × 主题 × 层级) → 3–7 本`**，每本一句可核对的理由。
所以管道末端必须有一个**选材（selection）阶段**，它不是点积：去重（work 级）、
多样性约束（每主题最多 N 本、每作者最多 1 本）、截断、理由拼装。

配套的一点：一份没有「为什么读这本」的书单是排行榜，不是书单。这不必违反
「不做全量书评生成」的非目标 —— 理由串可以**确定性拼装**自维度事实：

> `O'Reilly · 核心开发者作者 · HN 提及 34 次（2016–2024）· 主题半衰期 25 年 · 深度 72/100`

零 LLM 散文，完全可追溯，而且比一个 78.3 分更能让访客判断要不要读。

## 五、优先级建议

按「阻止首版出错」排序，不按工作量排：

1. **m1**（commit）—— 五秒钟。
2. **B2 的 dry-run** —— 一天，且它的输出是 B1/B3/M1 所有决定的输入。**先做这个，再改公式。**
3. **B1 + B3 + B4 + B5** —— 改 `scoring-standard.md`，一次改完（都是同一处模型问题的不同表现）。
4. **M2** —— 解掉后 Phase 1 不再是跨仓库阻塞，排期整体前移。
5. **§三 的选材层 + M6 去重** —— 决定输出是「书单」还是「排行榜」。
6. **M8 的 gold 标注 + §五 的 gold set 门禁** —— 把 AC-P2① 从「看着没问题」变成一个数。
7. 其余按 M / m 编号顺序。

修法与新的落地顺序见 [system-design.md](../spec/system-design.md)。
