# 实现评审（第三轮）—— 面向公开上线

> 日期: 2026-08-05
> 评审对象: 全仓库（约 3,700 行 Go + 内嵌 SPA + 参照清单 + CI），基线 commit `0f52b4c`
> 评审口径: 前两轮问「实现兑现了设计吗」。这一轮换一个问题 ——
> **把它接上真实语料、挂上公开域名，第一周会在哪里出事？**
> 结论: 前两轮的修法确实立住了（三层边界真实、A1–A4 的回归测试都在打正确的接缝上）。
> 本轮新发现 **4 个阻塞级**缺陷，其中 3 个的共同特征是「守住了正门、漏了侧门」——
> 同一条规格约束在另一条代码路径上没有被执行。另有 6 项上线第一周会咬人的问题。
> 前两轮见 [review-2026-08-04.md](review-2026-08-04.md)、[review-2026-08-05.md](review-2026-08-05.md)。

先说好的部分，它决定了下面的语气：`score` 确实离线、`published_run` 确实原子、
`spa-parity.js` 是这套系统里最聪明的一件工程 —— 它把「同一个公式有两份实现」这个
无法用编译器约束的风险，变成了一条可执行的断言。本轮所有发现都建立在这个水准之上，
且**没有一个是前两轮已判定过的问题复发**。

## 一、阻塞级

### A1 没有出版社的书被判成 tier 3 且 `T = measured` —— 权威维的闸门整个失效

**根因是一次多余的二次归一化。** `Publisher()` 的输出被当成它自己的输入喂了回去：

| 步骤 | 位置 | 发生了什么 |
|------|------|-----------|
| 导入 | [import.go:158](../../internal/corpus/import.go) | `Publisher("")` → `{Norm: "unknown", Tier: 4}`，`editions.publisher_norm` 写入字符串 `"unknown"` |
| 打分 | [engine.go:731](../../internal/score/engine.go) | 拿 `publisher_norm` **再归一一次**：`Publisher("unknown")` —— 此时 `n != ""`，表里又没有哪个 key 是 `"unknown"` 的子串 → 落到「表外但确实有名字」那条兜底 → **`Tier: 3`** |

于是 `trust()`（[dims.go:102](../../internal/score/dims.go)）里 `pubKnown = tier <= 3` 成立：

```
应有: raw = 0.6·25 + 0.4·25 = 25,  state = shrunk    （没有出版社 = 没有这一维的证据）
实际: raw = 0.6·50 + 0.4·25 = 40,  state = measured  （凭空多出 15 分，且被当成实测）
```

两个后果，第二个更严重：

1. **闸门失效**：`timeless` / `to-read-next` / `read-and-loved` 都声明 `needs: {T: measured}`。
   一本连出版社都没有的书，凭这个 bug 拿到 `measured` 就通过了「权威维必须有实测证据」这道硬门。
2. ⚠️ **CDF 被污染，review B5 的病从后门复发**。实测出版社覆盖率 66%
   （[data-baseline](../spec/data-baseline.md)）→ 约 **700 本**无出版社的书会全部带着 `raw = 40`
   进入 T 维的 measured 集合。而 §3 的设计前提正是「CDF **只**由 measured 构建，
   shrunk 不参与，否则大量并列值会把有数据的书压进一条窄带」。700 个并列值正是那个被
   明令排除的东西 —— 只不过这次它是伪装成 measured 混进来的。

演示语料掩盖了它：seed 里每本书都有出版社，所以这条路径从未被走到。

**修**：`Publisher()` 把 `"unknown"` 与空串一视同仁（`Tier: 4`）；补一条**幂等性**断言
`Publisher(Publisher(x).Norm) ≡ Publisher(x)` —— 这才是二次归一化架构真正依赖的不变量，
只修 `"unknown"` 一个值等于继续赌表里没有第二个反例。

### A2 时间过滤器在消费「已知被污染」的日期 —— R-1 从正门溜了回来

F 维守住了（不可信来源一律 `unknown`，`snapshot` 的三种来源都不在可信名单里）。
**但 preset 的时间过滤器没有守。**

`loadWorkInputs` 聚合 `FirstPubdate` / `LatestPubdate` 时**完全不看来源**
（[engine.go:739-747](../../internal/score/engine.go)）—— `mtime-fallback` 的日期照收；
而 `pubdate_within_months` 用的正是 `LatestPubdate`（[engine.go:297-299](../../internal/score/engine.go)）。

具体漏洞链（多版次的书，真实语料里 3 组以上）：

```
版次 A（有 ISBN，ingest 写入）: pubdate=2015-06-01  source=google
版次 B（无 ISBN，snapshot 兜底）: pubdate=2026-07-11  source=mtime-fallback
  → LatestPubdate = 2026-07-11        ✓ 过 pubdate_within_months: 12
  → PubdateSource  = "google"         ✓ 过 pubdate_source 白名单
  → F state        = measured         ✓ 过 needs: {F: measured}
  ⇒ 一本 2015 年的书堂堂正正进入「近一年新书」
```

这就是 R-1 描述的失效模式本身：「今年新书榜塞满老书 → 整站可信度一次性崩塌」。
477 本被 mtime 写成 2026 的书是这条链的燃料，而 `fresh-releases` 是唯一按时间取书的榜。

镜像问题在 `timeless`：`min_age_years` 看 `FirstPubdate`（[engine.go:290-292](../../internal/score/engine.go)），
同样吃污染日期 —— 方向相反，把该上榜的老书挡在外面。**review A2 的回归测试之所以通过，
只是因为 seed 里那本 mtime 书的日期恰好是 2013**（[seed.go:87](../../internal/corpus/seed.go)）；
生产语料里污染值是 2026，测试形状与生产形状不一致。

**修**：`FirstPubdate` / `LatestPubdate` 的聚合剔除 `mtime-fallback` 与 `unknown`
（`calibre` 来源保留 —— 它的 pubdate ≠ mtime，够不上 F 维的标准但作年龄证据是合理的）；
`pubdate_within_months` 与 `pubdate_year` 直接改用 `TrustedPubdate`。
新增一条「近期 mtime + 更早的可信日期」双版次语料的回归测试，形状对齐生产。

### A3 评分证据的真实刷新周期是 180 天，不是规格写的 30 天

`architecture §5` 定：评分类 TTL 30 天、元数据类 180 天。代码里两个常量都对，
但**评分行永远等不到被检查** —— 它被 180 天的查询标记挡在门外：

| 源 | 闸门 | 后果 |
|----|------|------|
| Google | [facts.go:229](../../internal/facts/facts.go) `isFresh(google_query, …)` 命中即 return | `google_books` 那行的 30 天 TTL 从来没被求值过 |
| OpenLibrary | [facts.go:274-277](../../internal/facts/facts.go) 同样在标记处 return | 连**第二跳**（`/works/{k}/ratings.json`）都不会发生 |

两个源要分别对待，因为它们的形状不同：

- **Google 一次请求同时返回 volume id 与评分** —— 所以把「映射」缓存得比「评分」更久
  没有任何收益：不重发那个请求，评分就刷不了。命中时标记应当用**评分 TTL**，
  只有「查不到」才值得压 180 天（没有东西可刷）。
- **OpenLibrary 是两跳**：ISBN → work key 确实稳定（180 天合理），但它不能把第二跳
  一起挡住。已有 `works.ol_work_id` 存着第一跳的结果，标记新鲜时应当直接拿它去刷评分。

**修**：Google 的查询标记按 `found` 分别用 30 / 180 天；OpenLibrary 保留 180 天标记，
但标记新鲜时改走「用 `ol_work_id` 只刷第二跳」的短路径。补测试断言 31 天后评分会被重取、
而 ISBN→work 的映射不会被重查。

### A4 `evidence` 以 `work_id` 绑定 → 改一个书名就静默丢证据；也是聚类升级的地雷

摄入侧做对了一半：评分行按**外部实体 id** 存（volume id / OL work id），
所以同一 work 的多个版次不会把同一份评分计两遍。但每行还顺手记下了写入当时的
`work_id`（[facts.go:394-406](../../internal/facts/facts.go)），而消费侧就 join 在这一列上
（[engine.go:805](../../internal/score/engine.go)）。

`work_id` 是 `姓氏 + 规范标题` 算出来的**派生键**。于是：

> 在 calibre 里修掉一个书名 typo → `work_id` 变 → 新 work 对不上旧 evidence →
> **这本书的 A 维静默消失**，且因为查询标记还新鲜（见 A3），最长 180 天不会被重抓。
> 补元数据是文档反复鼓励库主人做的事（用户故事 3），这个动作本身会打掉证据。

更要紧的是它给已登记的计划埋了雷：[homelab-deploy §3.4](../guide/deploy.md) 写着
「OL work id 升级聚类键，等数据攒够再切」。真去切的那天，`evidence` / `labels` /
`overrides` 三张按 `work_id` 键的表会**整体失联** —— 那不是切个开关，是一次数据迁移。

**修**：读取时解析，而不是信任写入时的快照。用 `editions.google_volume_id` /
`editions.isbn13` / `works.ol_work_id` 建索引，把 evidence 的 `source_id` 映射到当前
work，`evidence.work_id` 降级为排障用的提示列。顺带把它从 `factsHash` 里去掉 ——
事实是 `(source, source_id, payload)`，「哪个 work」是语料侧的信息，已由 `corpus_id` 覆盖。

同时修一个被这条掩盖的测试保真度问题：**seed 的 evidence 键与生产不一致**
（seed 用 `isbn:<isbn>`，生产用裸 volume id / OL work id，[seed.go:170-181](../../internal/corpus/seed.go)），
所以生产的键格式从未被任何测试走到。

## 二、重要 —— 上线第一周会咬人

### B1 「榜单静默过期」的警报覆盖不到最可能的过期方式

[homelab-deploy §3.3](../guide/deploy.md) 把 `readlist_last_score_unix` 称为
「静默过期的唯一警报」。但 **`score` 在陈旧 facts 上每晚照样成功** ——
`snapshot` 或 `ingest` 连挂一个月，这个指标依然常绿，全站数据冻结而无人知晓。
而这两个作业恰恰是更容易挂的：一个依赖 calibre 卷还在、另一个依赖外部配额。

`ingest` 甚至**根本不写 `runs` 行**（[facts.go:76-104](../../internal/facts/facts.go)，
对比 `snapshot` 有写：[import.go:226](../../internal/corpus/import.go)）。于是 `architecture §7`
承诺的「外部 API 请求数、429 数、当日剩余配额估算」在库里压根不存在 ——
唯一的痕迹是 pod 日志，而 pod 日志会随 `successfulJobsHistoryLimit: 1` 滚掉。

**修**：`ingest` 落一条 `kind='ingest'` 的 run（`Stats` 已经是现成的结构体）；
`/metrics` 补 `last_snapshot_unix` / `last_ingest_unix` / `orphan_rows` /
`pubdate_mtime_fallback` / `ingest_requests` / `ingest_throttled` / 逐维 `measured` 计数
（后者就是 system-design §7 要的 `measured_ratio[dim]`，也是判别力的直接度量）。

### B2 每个请求全库扫描 + 单连接 + 零 HTTP 缓存 → 爬虫能让唯一副本自杀

数据每天只变一次，但每个内容请求都要重新拉一遍 works+editions（约 2.5 千行）、
dim_scores（约 1.4 万行）与 reading（[queries.go:103-117](../../internal/api/queries.go)），
而 `SetMaxOpenConns(1)`（[store.go:45](../../internal/store/store.go)）把所有请求串行到一条连接上。

叠加效应比单看任何一条都糟：

> 爬虫一阵突发 → 请求在唯一连接上排队 → `/healthz`（也查库）排在后面 →
> 超过 livenessProbe 的默认 `timeoutSeconds: 1`（[readlist.yaml:86-89](../../deploy/oracle/readlist.yaml) 没设）
> → **kubelet 在高负载时杀掉唯一副本**。

这是自伤，边缘限流挡不住 —— 限流阈值之下的正常流量就能触发。

**修**（按性价比）：
1. 进程内按 `run_id` 缓存快照 —— 命中时每请求只剩一次 `published_run` 单行读。
   这一条几乎消灭全部重复 IO，也顺带让「连接池只有 1」不再是瓶颈；
2. 内容端点加 `ETag: run_id` + `Cache-Control` 并处理 `If-None-Match` →
   Cloudflare 能吸掉绝大部分公开流量，免费额度内源站近乎零压力；
3. livenessProbe 换到一个**不碰数据库**的静态端点（readiness 保留查库语义），并显式给
   探针 `timeoutSeconds`；
4. `http.Server` 补 `ReadTimeout` / `WriteTimeout` / `IdleTimeout`
   （[main.go:351-355](../../cmd/readlist/main.go) 只有 `ReadHeaderTimeout`，而 matrix 响应有几十 KB）。

> 连接池维持 1 不动：注释里防的「两个 cron 并发写」其实是**跨进程**问题，靠的是 SQLite
> 文件锁 + `busy_timeout`，与进程内连接数无关；但 `gcRuns` 那句「同一事务上边读边写会卡死」
> 说明代码已经绕着这个上限写了。有了第 1 条之后收益也不大，不值得为它引入风险。

### B3 `/metrics` 每次抓取重扫 1.4 万行 dim_scores

`gradesForRun`（[queries.go:239-264](../../internal/api/queries.go)）每 15–30 秒全表扫一遍，
而 `grade_counts` 在发布时就已经算好并存进了 `runs.metrics`（[engine.go:422](../../internal/score/engine.go)）。

**修**：直接读那个字段，回退路径才现算。

### B4 权重滑块 —— 核心卖点目前是装饰性的；`matrix` 端点零消费者

滑块只在当前榜已选出的约 20 本内重排（`app.js` 自己也明说了这个边界）。
而专为全库重排设计的 `matrix` 端点 —— 有 immutable 缓存、有 e2e 断言、有 404 校验 ——
**没有任何消费者**：SPA 从未 fetch 过它。

review-08-05 留下的顾虑是「客户端复刻选材会与后端漂移」。但这个仓库已经发明了对付漂移的
武器：`spa-parity.js`。贪心选材是确定性的（约 15 行 JS），把 filters/needs 需要的 facet
（`pubdate_source` / `personal_rating` / 可信日期 / `topics`）加进 matrix，客户端复刻
`Combine` + `Select`，再让 parity 脚本逐位比对即可 —— 与 TBS 公式当初的处置完全同构。

**判断**：做完它，「拖权重 → 榜外的书真的能进来」才成立，这是与通用书榜的核心差异；
不做，就该把 `matrix` 端点删掉 —— 维护一个零消费者的端点是纯负债。本轮不动，
但这是**产品层第一优先**。

### B5 `publisher_map` 写了没人读，却被列为「不可再生、必须夜备」

| 文档说 | 代码做 |
|--------|--------|
| 「一次性人工归一 + 规则积累」、「重建要重新人工判断」→ 纳入夜备（NFR-16）、PVC 备份标签里点名 | 每夜被硬编码规则表 `INSERT OR REPLACE` 覆盖（[import.go:149-165](../../internal/corpus/import.go)），且**没有任何读取方** —— `Publisher()` 用的是 `publisher.go` 里的内置表 |

两条路：让它真的成为人工覆盖源，或者从备份清单里除名。前者有实际价值 ——
内置表覆盖不到的出版社变体（真实语料里必然有）现在无处可归。

**修**：加 `source` 列（`rules` / `manual`）；`Import` 只覆盖 `rules` 行，并把 `manual`
行当作覆盖源应用。人工覆盖只需给出规范名，tier 由现有规则表从规范名推出。

### B6 `overrides` / `mention_overrides` 零入口 —— R-3 与 §13 的承诺没有落点

`overrides` 表存在、进了 `factsHash`（[engine.go:582](../../internal/score/engine.go)）、
被写进备份清单，但**没有任何消费者**。`mention_overrides` 表**根本不存在**。

于是两处承诺悬空：R-3 的「保留 `objectID` 供人工逐条否决」（HN 误匹配的唯一兜底）、
以及 [system-design §13](../spec/system-design.md) 要库主人决定的「`timeless` 接受一层人工
curation 吗 → 加 `pin`/`veto`」—— 想选「接受」也没有开关可拨。

**修**：`mention_overrides` 建表 + `loadMentions` 过滤 `verdict='reject'`；
`overrides` 支持 `veto` / `pin`（值为榜 id 或 `*`），在选材层生效。

## 三、产品层

| # | 问题 | 说明 |
|---|------|------|
| C1 | **hash 路由让每本书都不可索引、不可分享** | 公开内容站的全部内容在 JS 之后：`#/book/…` 搜索引擎抓不到，分享出去没有预览卡片，sitemap 无从谈起。SPA 的数据 handler 已经有全部素材，用 `html/template` 对 list/detail/catalog 三类页做 SSR（或至少 path 路由 + OG 标签 + sitemap）与「零依赖前端」并不冲突 |
| C2 | **主题小榜还没出生** | [system-design §5](../spec/system-design.md) 判断「主导航是目标榜，二级是主题×层级小榜 —— 后者才是访客真正会收藏的东西」，且明说不需要新代码。`ai-llm` 已经证明了机制可用，剩下的纯是产品选择 |
| C3 | 目录页 2,054 行纯列表，无搜索无筛选 | 数据已全在客户端，二十行的事，却是目录页可用性的分水岭 |
| C4 | 「可复现」只活在 CLI 里 | `lists` 保留最近 5 个 run，`readlist diff` 的能力已经有了。一个「本周谁进了、谁出了、因为哪一维」的页面 + RSS，成本极低，却把「可解释、可复算」从承诺变成访客看得见的东西，也是工程师受众唯一的自然订阅渠道 |
| C5 | 首页导航把 `/metrics` 裸露给公开访客 | 运维端点不该出现在公开导航里 |

产品层最后一句提醒，与代码无关但比任何代码优化都靠前：北极星指标 `to-read-next` 的
内容完全取决于 Phase 0 手工补录与 KOReader 接入；`eval/gold.yaml` 的防作弊价值随每次
权重调整持续流失。这两件只有库主人能做的事，仍然是项目的真实瓶颈。

## 五、优先级与本轮处置

按「阻止公开后翻车」排序，不按工作量：

| 顺序 | 项 | 为什么这个次序 |
|------|----|--------------|

### 顺带定下的三件事

修 A2 时撞上一处规格空白，必须做判断而不是照着代码改，所以单独记下来：

1. **两个时间过滤器语义不对称**（已写进 [scoring-standard §3](../spec/scoring-standard.md) 的 F 维）。
   「够不够新」日期未知 → 排除；「够不够老」日期未知 → 放行 + 理由串披露「年龄未核实」。
   起因是 review B1 的原话「timeless 不关心出版日期」只对 `weights` 成立 ——
   `timeless` 的 `filters.min_age_years` **是**一个出版日期闸门。两者若都 fail-closed，
   477 本 mtime 污染的书会从旗舰榜整批消失，也就是 B1 判定过的那个模型错误。
2. **`requirements.md` 有两个 NFR-17**（容量与安全），而两个 ID 都被别处引用过
   （`homelab-deploy.md` 指容量、`bdd/ingestion.feature` 指安全）。安全那条改为
   **NFR-18** 并同步了 feature 文件；新增 NFR-19（抗爬）、NFR-20（可观测）、FR-36/37（人工干预）。
3. **`pin` 必须自我披露**。人工 curation 绕过全部准入是它的用途，但公开榜上必须让读者
   分清哪一条是算出来的 —— 理由串写「人工置顶」，且 `coverage` 照实显示（演示语料里那本
   被置顶的书写着「按 2/5 维评出」）。「可解释」这条承诺的全部价值就在这个区分上。
